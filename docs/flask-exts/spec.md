## 1. 项目定位

Flask-Exts 是一个面向 Flask 的扩展集合，用于把常见的 Web 基础能力拆成可组合模块：

- 扩展注册与生命周期管理
- SQLAlchemy 数据访问
- Admin / ModelView / DataBackend
- WTForms 表单与 CSRF
- 用户存储与认证
- 令牌、2FA、加密与安全控制
- 邮件、前端资源、国际化、门户页面

它不是一个固定的大型 CMS，也不是只有单一“一体化”框架，而是“基础能力 + 可插拔扩展”的组合式设计。

## 3. 设计目标

1. 把通用能力拆成独立扩展，便于按需组合。
2. 把初始化过程从“业务感知”中分离出来，形成稳定的扩展生命周期。
3. 在后台视图、数据访问和表单层之间做解耦，减少单点耦合。
4. 将认证、安全、用户存储、Admin 等能力尽量标准化，复用同一套应用上下文。
5. 让工程在早期仍可演进，同时保留对测试、审查和扩展的可验证性。

## 3.1 首版缺口与优先级（历史快照）

> 本节是 v0.1 建立时的缺口清单；其中扩展作者契约、约束、依赖原则、范围外声明等已在 `plugin.md`、`architecture.md`、`database.md` 展开。本节保留为历史优先级记录，未逐项复核，阅读时以专题文档为准。

如果只问“还缺什么”，优先级建议如下：

1. 扩展作者的最小契约：定义扩展必须提供什么接口、如何注册、如何初始化、如何关闭。
2. 约束与不变式：明确禁止做什么、必须满足什么语义约束，例如依赖不能循环、初始化前后状态必须稳定。
3. 模块依赖方向/分层原则：明确哪些模块可依赖哪些模块，避免“可组合”变成隐藏耦合。
4. 范围外声明：说明哪些能力不属于本项目，避免无边界扩张。
5. 版本与兼容性策略：说明预期的发布节奏、兼容方式和升级约束。
6. 关键决策的替代方案与理由：让设计取舍可追溯，而不是只留结论。
7. 非功能需求的归属与优先级：如安全、性能、可观测性、可维护性应该落在哪一层文档中。
8. 设计成功标准：定义什么时候可以认为本设计“够成熟”，便于验证和复盘。

这些项不是“可选增强”，而是让扩展集合真正具备可审查、可维护、可扩展的最小工程性要求。

## 4. 关键设计取舍

### 4.1 扩展生命周期

项目采用“注册 + 依赖排序 + 两阶段初始化”的方式：

- `init_app()`：建立扩展实例并绑定到应用
- `post_init()`：在所有扩展初始化后进行跨扩展组装
- `shutdown()`：按逆序清理资源

这样可以减少模块之间的强依赖和隐式初始化顺序耦合。

### 4.2 Registry / Manager 模式

扩展管理是核心抽象：

- Registry 保存扩展注册表和依赖关系
- Manager 对外提供统一入口
- 业务代码不直接依赖每个扩展的具体实现

这有利于扩展增删、依赖检查和测试隔离。

### 4.3 Admin 与 DataBackend 解耦

后台视图依赖 `ModelView` 与 `DataBackend` 的组合：

- 视图负责展示与交互
- 数据后端负责查询、筛选、排序、导出

此设计让视图层和数据访问层可独立演进。

### 4.4 安全控制集中化

安全相关能力尽量放到统一的安全扩展和用户存储抽象中：

- 密码哈希
- 令牌动作
- 2FA / TOTP
- JWT / 令牌声明
- CSRF
- 授权判定

这样可以让不同扩展共享同一套安全边界，而不是到处复制逻辑。

```text
flask_exts/
├── extension_core/     # 生命周期与扩展注册

├── forms/              # 表单与 CSRF
├── security/           # 认证、授权、令牌、2FA

├── emailer/            # 邮件发送能力
├── frontend/           # 模板与脚本资源管理
├── portal/             # 门户页
├── commands.py         # CLI
├── proxies.py          # 应用上下文代理
├── signals.py          # 事件信号
```
