## 0. 审查定位

代码审查有三种常见级别：

| 级别 | 审查者 | 目的 | 适用 |
| --- | --- | --- | --- |
| 第一方 | 作者自审 | 提交前自查 | 日常开发 |
| 第二方 | 团队同行 | PR 合并前评审 | 常规变更 |
| 第三方 | 独立审查者/外部团队 | 发布前、安全评审、合规审计 | 本文范围 |

**独立第三方审查**的特点：

- 审查者不是代码作者；
- 审查者不参与本次实现；
- 审查者默认**只读**，不直接修改代码；
- 结论必须基于可复现的证据，而不是印象；
- 报告独立提交，作者/维护者负责修复，审查者负责复审关闭。

本文不是“当前缺陷列表”，而是**审查方法与验收标准**。当前已知问题作为审查输入的一部分，不是审查结论本身。

## 1. 独立性要求

### 1.1 人员独立

审查者必须满足：

- 未参与被审查 commit 的实现；
- 未参与该功能的需求/设计决策（或已声明）；
- 与项目无未声明的利益冲突；
- 不对修复方案拥有唯一决定权；
- 不以“帮忙改代码”代替审查。

### 1.2 环境独立

- 使用干净 checkout，固定 commit/tag；
- 使用独立虚拟环境，不复用作者本地状态；
- 不依赖未提交的本地修改；
- 数据库使用隔离实例/临时文件，不连接生产；
- 测试/工具输出保留日志。

### 1.3 证据独立

- 每个结论必须能由第三方按报告步骤复现；
- 报告记录 commit、环境、命令、输入、输出；
- 安全 PoC 在隔离环境执行，报告中脱敏；
- 不能复现的怀疑标“待确认”，不能当作已确认缺陷。

### 1.4 结论独立

- 审查者不因时间压力降低严重度；
- 不因“历史一直这样”忽略问题；
- 不把“测试通过”当作“无缺陷”；
- 区分“设计取舍”和“实现缺陷”。

## 2. 审查范围与输入

### 2.1 审查对象

至少包括：

- 指定 commit/tag 的 `src/flask_exts/`
- `tests/`
- `pyproject.toml`、`.github/workflows/`
- `flask-exts/docs/`（Sphinx）
- `examples/`
- `README.md`、`AGENTS.md`

### 2.2 审查输入文档

| 文档 | 用途 |
| --- | --- |
| `requirements.md` | 预期行为、`REQ-*`、验收标准 |
| `architecture.md` | 系统边界、模块依赖、生命周期、状态所有权 |
| `spec.md` | 设计模式、实现细节、当前观察 |
| `view.md` | View/Admin 领域行为与已知问题 |
| `security.md` | 威胁模型、安全边界、`SEC-*` 风险 |
| `testing.md` | 测试策略、用例、覆盖率/CI 计划 |
| `demo.md` | 可运行验收与配置基线 |
| 仓库 `AGENTS.md` | 开发规范、变更边界 |

### 2.3 审查范围声明

报告开头必须声明：

- 审查 commit/tag；
- 审查的模块/文件；
- 未审查的模块及原因；
- 使用的环境与工具版本；
- 是否包含安全审查、性能审查、兼容性审查；
- 是否包含历史遗留问题。

## 3. 审查级别

| 级别 | 触发条件 | 输出 |
| --- | --- | --- |
| L1 快速审查 | 小改动、低风险 | 简短报告 + 阻塞项 |
| L2 标准审查 | 常规功能/修复 | 完整检查清单 + 报告 |
| L3 发布/安全审查 | 公开发布、安全相关、架构变更 | L2 + 威胁建模 + 兼容性 + 发布检查 |
| L4 合规审查 | 受监管/合同要求 | L3 + 需求追溯 + 签核记录 |

本项目建议：

- 普通 PR：L1/L2；
- 认证/授权/令牌/CSRF/TFA/依赖/发布：L3；
- 外部合同/安全认证：L4。

## 4. 严重度定义

| 等级 | 定义 | 示例 | 发布影响 |
| --- | --- | --- | --- |
| **Critical** | 可直接导致远程代码执行、认证绕过、大规模数据泄露/丢失、密钥泄露 | RCE、SQL 注入、任意文件读写、admin 无认证 | **阻塞发布** |
| **High** | 可导致账号接管、权限提升、持久化 XSS、TFA 绕过、令牌伪造、严重 DoS | 弱令牌、JWT 无 TFA、inactive admin 仍可访问 | **阻塞发布**，或需书面风险接受 |
| **Medium** | 需要特定条件/组合利用，或造成局部数据错误/信息泄露/性能问题 | 一对多计数偏大、缺少邮箱格式校验、缺少限流（视暴露面定级） | 修复或登记风险接受 |
| **Low** | 可维护性、命名、边界文档、轻微 UX/日志问题 | RowsAction 命名混淆、死分支 | 可排期 |
| **Info** | 建议/观察，不构成缺陷 | 命名建议、文档改进 | 不阻塞 |

严重度判定要考虑：

- 可达性（匿名/普通用户/admin/本地）；
- 前置条件（是否需要密码、配置、特定数据库）；
- 影响范围（单用户/全站/数据完整性）；
- 可利用性（稳定复现/理论）；
- 现有补偿控制（WAF、网络隔离、限流）。

## 5. 审查流程

```text
1. 受理
   ├─ 确认 commit/tag、范围、风险等级
   ├─ 确认独立性/利益冲突
   └─ 确认交付时间与报告格式

2. 预读
   ├─ requirements / architecture / security / testing
   ├─ diff 与变更文件
   └─ 相关 issue/CHANGES

3. 自动化基线
   ├─ pytest / coverage
   ├─ ruff / djlint
   ├─ sphinx -W
   ├─ pip-audit（如可用）
   └─ 依赖/许可证检查

4. 人工审查
   ├─ 契约符合性
   ├─ 架构/边界
   ├─ 正确性/数据
   ├─ 安全
   ├─ 测试质量
   ├─ 兼容性/性能/可靠性
   └─ 文档/示例

5. 复现与定级
   ├─ 编写最小复现
   ├─ 确认影响与前置条件
   └─ 定级 Critical/High/Medium/Low/Info

6. 报告
   ├─ 汇总表
   ├─ 逐条证据
   ├─ 未覆盖范围
   └─ 独立性声明

7. 作者响应
   ├─ 接受/拒绝/风险接受
   ├─ 修复计划/负责人/期限
   └─ 补充测试

8. 复审与关闭
   ├─ 复核修复
   ├─ 回归测试
   ├─ 更新报告状态
   └─ 签核
```

### 5.1 受理检查单

- [ ] commit/tag 固定
- [ ] 审查范围明确
- [ ] 独立性/冲突声明
- [ ] 输入文档版本明确
- [ ] 数据库/网络环境隔离
- [ ] 报告格式与截止时间明确

### 5.2 自动化基线

自动化基线命令只在 `testing.md` 第 11.2 节维护；审查时按该节执行，并只跑与变更相关的文件。

> 不要为了审查安装新工具；需要新依赖时先申请。已有 Ruff/djLint 历史问题只检查变更文件。

## 6. 审查维度与检查清单

### 6.1 契约符合性

- [ ] 变更行为能找到对应 `REQ-*`
- [ ] 新增/修改行为已更新 `requirements.md`
- [ ] 错误路径、边界、不变量有定义
- [ ] 测试覆盖 `REQ-*` 的验收标准
- [ ] 没有把 `known-gap`/`proposed` 当作已完成

### 6.2 架构与边界

- [ ] 模块依赖方向符合 `architecture.md`
- [ ] 没有新增循环依赖
- [ ] 扩展生命周期（init/post_init/shutdown）未被破坏
- [ ] `db` 单例/会话作用域未被误用
- [ ] 跨模块协作优先用 proxies/signals，而非硬编码
- [ ] 没有把业务逻辑塞进 `extension_core`/`datastore`

### 6.3 正确性与数据完整性

- [ ] CRUD 最终数据库状态正确
- [ ] 事务失败回滚，不留下部分写入
- [ ] 一对多 JOIN 的计数/分页正确
- [ ] 复合主键/字符串主键正确编码
- [ ] 唯一约束/外键/级联行为符合模型
- [ ] Inline 子记录归属正确
- [ ] 日期/时区/空值/枚举边界正确

### 6.4 安全

- [ ] 认证：登录失败统一提示、dummy hash、TFA pending 不建立会话
- [ ] 授权：默认拒绝、`allow_access`、`requires_active`、admin/super_admin
- [ ] 会话：密码变更失效、登出清理、Cookie 安全属性
- [ ] 令牌：签名、过期、篡改、用户不存在、密码/邮箱变更失效
- [ ] CSRF：默认开启、缺失/无效/过期拒绝、JSON/AJAX 携带 token
- [ ] TFA：TOTP 加密存储、恢复码哈希、失败限流/锁定、JWT 是否绕过
- [ ] 开放重定向：外部/畸形 URL 拒绝
- [ ] 密钥：`SECRET_KEY`/`JWT_SECRET_KEY`/CSRF 分离；轮换影响
- [ ] 日志：不记录密码/令牌/TOTP secret/恢复码
- [ ] 依赖：无已知高危漏洞、无不必要的新依赖
- [ ] 文件上传：类型/大小/路径/覆盖策略
- [ ] 模板：自动转义、`Markup`/`safe` 使用是否可信

### 6.5 测试质量

- [ ] 测试从契约推导，不从实现反推
- [ ] 正例/反例/边界/权限/错误路径
- [ ] 测试独立、可重排、无模块级可变全局
- [ ] 不依赖固定时间/网络/执行顺序
- [ ] 断言最终状态与关键响应，不只断言状态码
- [ ] 安全用例覆盖 `SEC-*`/`REQ-*`
- [ ] 覆盖率基线/增量门槛
- [ ] 没有无理由 `skip`/`xfail`

### 6.6 API 兼容性与发布

- [ ] 公共 API 变更符合 SemVer
- [ ] 废弃/迁移说明
- [ ] 版本号未被随意修改
- [ ] 依赖版本范围合理
- [ ] 构建/PyPI 发布流程可复现
- [ ] 示例/文档与 API 一致

### 6.7 性能与可靠性

- [ ] 列表/搜索/Inline 无明显 N+1
- [ ] 分页/导出有上限
- [ ] 大结果集不一次性加载
- [ ] DB/SMTP 失败有处理
- [ ] 超时/重试/回滚策略明确
- [ ] 内存/连接泄漏风险

### 6.8 前端与模板

- [ ] Jinja 自动转义未被绕过
- [ ] AJAX 请求带 CSRF
- [ ] 用户输入不进入 `|safe`/`Markup`
- [ ] 模板覆盖保留 `super()`
- [ ] 静态资源/vendor 未被手改
- [ ] 响应头缺失（CSP/HSTS/X-Frame-Options）是否由部署层补偿

### 6.9 文档与示例

- [ ] 行为变化同步 `requirements.md`
- [ ] 架构/模块变化同步 `architecture.md`
- [ ] View/安全变化同步 `view.md`/`security.md`
- [ ] 测试变化同步 `testing.md`
- [ ] demo 变化同步 `demo.md` 与 `examples/README.rst`
- [ ] 文档命令/配置/默认值可执行
- [ ] 数据快照日期更新

### 6.10 供应链与配置

- [ ] 新依赖必要、许可证兼容、版本锁定合理
- [ ] 没有提交密钥/凭据/`.env`
- [ ] CI 覆盖测试/文档/示例
- [ ] 发布 workflow 有测试门禁
- [ ] 配置文件默认值安全（CSRF、Cookie、密钥）

## 7. 证据与复现规则

### 7.1 每条发现必须包含

| 字段 | 要求 |
| --- | --- |
| ID | `CR-F-001` |
| 标题 | 一句话说明 |
| 严重度 | Critical/High/Medium/Low/Info |
| 位置 | 文件:行号 + commit |
| 前置条件 | 角色、配置、数据、环境 |
| 复现步骤 | 最小、可执行 |
| 实际结果 | 日志/响应/DB 状态 |
| 期望结果 | 对应 `REQ-*`/安全边界 |
| 影响 | 可达性、范围、后果 |
| 建议 | 修复方向，不强制具体实现 |
| 证据 | 命令/测试/日志（脱敏） |
| 状态 | Open/Accepted/Fixed/Verified/Won't fix/Risk accepted |

### 7.2 复现规则

- 使用隔离环境/临时数据库；
- 安全 PoC 不针对生产；
- 不破坏用户数据；
- 不包含真实密钥/令牌；
- 不能稳定复现的标“待确认”，不能定 High/Critical；
- 同一根因合并为一条，避免重复计数。

### 7.3 证据示例

```text
Commit: <sha>
Environment: Python 3.13, SQLite in-memory, CSRF disabled for test
Command:
  python -m pytest -q tests/integration/usercenter/test_user_view.py::test_tfa
Actual: ...
Expected: ...
```

## 9. 通过标准与签核

### 9.1 通过条件

- 无未关闭 Critical/High；
- Medium 已修复，或有负责人、期限、补偿控制与书面风险接受；
- 所有 P0 `REQ-*` 有测试覆盖；
- 安全相关变更已按 `security.md` 检查；
- CI 绿灯（测试/覆盖率/文档/示例）；
- 文档与实现一致；
- 审查报告已归档。

### 9.2 有条件通过

允许在以下情况有条件通过：

- 仅剩 Low/Info；
- Medium 有明确修复计划与风险接受；
- 不涉及认证/授权/令牌/CSRF/TFA/数据完整性；
- 有补偿控制（WAF/限流/监控/回滚方案）。

### 9.3 不通过

- 存在未关闭 Critical/High；
- 认证/授权/令牌/CSRF/TFA 边界不清；
- 无法复现的 High 但影响重大且无补偿控制；
- 测试无法证明关键路径；
- 文档/CHANGES 缺失导致发布不可审计。

### 9.4 签核

报告必须包含：

- 审查者身份与独立性声明；
- 审查 commit/tag；
- 结论（通过/有条件通过/不通过）；
- 未覆盖范围；
- 风险接受记录（如有）。

> 第三方审查是**技术评估**，不是法律认证、合规认证或安全保证。对外发布/合同场景需另行签署正式文件。

## 10. 复审与关闭

```text
发现 Open
  → 作者响应（接受/拒绝/风险接受）
  → 修复 + 测试
  → 审查者复核
      ├─ 通过 → Verified → Closed
      ├─ 未通过 → 重新打开
      └─ 风险接受 → Risk accepted（需负责人签字/记录）
```

复审要求：

- 使用修复后的 commit；
- 复跑原复现步骤；
- 复跑相关回归测试；
- 检查是否引入新问题；
- 更新报告状态，不删除历史发现。

## 11. 禁止行为与伦理

审查者不得：

- 在被审查代码中直接提交修复（除非另有授权）；
- 使用生产数据/真实用户信息做 PoC；
- 公开未修复的高危漏洞；
- 把猜测写成确定结论；
- 因个人偏好抬高/压低严重度；
- 隐藏未覆盖范围；
- 泄露密钥、令牌、个人信息。

审查者应当：

- 以证据为中心；
- 区分“设计取舍”和“实现缺陷”；
- 给出可执行的修复方向；
- 尊重作者，避免人身评价；
- 在报告中说明限制与不确定性。
