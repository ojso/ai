# AGENTS.md — flask-exts 文档维护指南

> 本文件是**本目录文档**的项目级规则，面向 AI 代理与人类贡献者。
> **本目录**：指**本文件所在目录**；不依赖外层目录名（`ai/`、`docs/`）是否存在或可见。
>
> **适用范围**：仅本目录下的 Markdown 文档，边界见第 1 节。项目代码、测试、示例、Sphinx 文档以仓库 `flask-exts/AGENTS.md` 和仓库内文档为准。
>
> **冲突处理**：涉及代码/依赖/提交/测试以仓库 `AGENTS.md` 为准；仅涉及本目录文档以本文件为准；无法判断时先询问，不自行扩大修改范围。仓库位置未确认或仓库 `AGENTS.md` 不可见时，仅按本文件执行，且不跨目录修改。
>
> **仓库位置**：代码仓库不在固定路径。每次任务/会话开始前，必须先向用户确认仓库的实际根目录（或确认本轮不访问仓库）；不得假定为 `flask-exts/`、当前目录或任何历史路径。确认后，本文及 `README.md` 中的 `flask-exts/...` 路径里，`flask-exts/` 表示该根目录，其余为仓库内相对路径。

允许修改：

- `README.md`

- `spec.md`
- `security.md`
- `testing.md`
- `demo.md`
- `glossary.md`

禁止修改（除非用户明确要求）：

## 2. 文档角色与依赖

依赖、约束与执行顺序分别见 `README.md` 第 2 节和第 6 节。需求、架构、安全及领域约束须相互校验；`testing.md` 从行为契约推导测试，仓库测试与 demo 提供实际证据。上述关系并不意味着每次都要线性修改全部文档。

本文件只管理当前文档目录；代码任务应由用户授权，并遵守代码仓库自身的 `AGENTS.md` 和实际工作流。仓库规则不可见时，本文件不能替代或推定仓库规则。

| 文档 | 负责 | 不负责 |
| --- | --- | --- |
| `README.md` | 索引、职责边界、单一事实源、更新规则 | 不承载具体技术事实 |
| `glossary.md` | 术语统一、英文/代码名、定义与使用规范 | 不替代实现细节 |
| `release.md` | 版本状态、影响范围、发布检查、回滚条件与代码审查清单 | 不替代需求/安全文档 |

| `architecture.md` | 系统上下文、模块依赖、生命周期、请求路径、状态所有权、关键决策、失败边界 | 不重复实现细节与安全清单 |
| `spec.md` | 项目全景、设计背景与 View/ModelView/DataBackend、Inline、AJAX、导出、模板；扩展注册、依赖、生命周期与作者契约；数据库边界、session、查询、数据所有权与事务 | 不重复完整契约/架构概览/安全威胁模型/测试用例；插件专题不重复具体页面行为 |
| `security.md` | 威胁模型、认证/授权、令牌、CSRF、TFA、JWT、风险与发布检查 | 不代替安全审计/渗透测试 |

## 3. 事实源与冲突处理

完整的事实源映射表只在 `README.md` 第 5 节维护；本节不复制。

冲突处理：

1. 先判断是“契约错”还是“实现错”。
2. 契约错：改 `requirements.md`，同步 `architecture.md`（边界/依赖）、`spec.md`（含 View/Admin）、`security.md`、`testing.md`、`demo.md`。
3. 实现错：保留契约，先在 `testing.md` 补失败用例，再改代码（需用户确认）。
4. 不允许把代码现状直接抄进文档来“消除冲突”。
5. 已确认实现不满足且无法立即修复：在契约“关联”字段登记问题或风险，分别按证据更新实现和验证状态；尚未核实的事实标“待核实”，不推断现状。

## 4. 修改前必须做

1. 向用户确认代码仓库的实际根目录；若本轮不访问仓库，记录“仓库位置未确认/本轮不访问”。
2. 阅读 `README.md` 与相关文档的目录。
3. 找到对应的 `REQ-*`；没有就判断是否需要新增契约。
4. 涉及当前行为时，只读查看源码/测试，不要修改。
5. 明确本次是：
   - 契约变更
   - 架构/设计说明
   - View/安全领域说明
   - 测试方案
   - 示例指南
   - 纯索引/状态更新
6. 确认不会新增重复事实源。

### 4.1 变更风险分级

按变更影响选择执行要求：

| 类型 | 例子 | 最低执行要求 |
| --- | --- | --- |
| 低风险 | 不改变行为的文档修润、局部重构 | 确认行为不变与影响范围；运行针对性检查，记录结果 |
| 常规变更 | 新增或修改一般功能/契约 | 确认契约与影响领域；设计测试并尽可能先验证失败，再实现、回归与同步文档 |
| 高风险 | 认证授权、数据/事务、公开 API、兼容性、发布 | 补完整影响评估、安全与兼容性验证及回滚方案；发布严格执行 `release.md` |

## 5. 修改规则

### 5.1 契约

- 一个新建 `REQ-*` 只描述一个可验证行为。
- 契约采用 `REQ-<领域>-<序号>`，分配与兼容规则以 `requirements.md` 第 1.1 节为准；领域先查 `glossary.md` 第 1.1 节，不自行发明缩写。
- 旧格式编号仍有效；不得擅自重编号、拆分或仅因换号改变契约状态。确需迁移时按 `requirements.md` 保留旧编号与关联。
- 编号永不复用；废弃或取代时保留历史，替代关系与适用范围按 `requirements.md` 第 2.1 节记录。
- 必须包含 `lifecycle`、`implementation`、`verification`、前置、输入、行为、输出/副作用、错误、不变量、验收和关联。
- 三维状态的取值与证据以 `requirements.md` 第 2 节为准；无依据不得标为已批准或验收通过。
- 已确认的缺口在“关联”字段登记 `SEC-*`、`C*`/`V-*` 或项目认可的问题记录；未核实的标“待核实”，不当作无缺口。
- 不要把“计划/应该”写成“已实现”，或把实现、测试设计和风险接受写成验收通过。

### 5.2 架构与领域文档

- `spec.md` 负责项目设计背景与 View/Admin、插件、数据库领域说明。
- `security.md` 负责安全领域细节；领域说明只链接契约，不复制整条 `REQ`。
- 模块行为变化时，先改契约，再改架构/领域说明。
- 代码审查结论与历史审查结论必须分开标注。

### 5.3 测试文档

- 用例从 `REQ-*` 推导，不从实现反推。
- 具体 `REQ → TC` 映射在 `requirements.md` 对应契约的“验收”字段维护；用例或测试代码中的 `REQ-*` 标注仅作辅助引用，不另建反向权威映射，也不证明断言正确或测试已运行。
- 测试用例使用 `TC-<领域>-<序号>`；本目录历史用例按 `testing.md` 第 6.3 节保留旧编号映射。测试层级记录在类型字段，不放入编号。后续变更须保留映射，不擅自修改仓库代码或外部引用。
- 各契约“验收”字段维护测试用例编号、实际测试入口和执行证据；按 `requirements.md` 第 2 节记录验证状态，参考 `testing.md` 第 6.2 节核对证据。
- 区分“现有 / 待补 / 待修 / 目标 / 规划”。
- 不把“测试计划”写成“测试已实现”。
- 覆盖率、性能目标必须注明是“基线”还是“目标”。

### 5.4 示例文档

- `demo.md` 的命令必须能实际执行；不能凭猜测写。
- 默认凭据必须标明“仅本地演示”。
- 不把 demo 当生产模板。
- 示例行为变化时，同步 `examples/README.rst`（需用户确认）。

### 5.5 索引文档

- `README.md` 只做索引、职责、单一事实源、状态和更新规则。
- 不复制具体命令、配置表、用例或代码细节。
- 文档角色/状态变化时更新 `README.md`。

### 5.6 AI 任务执行与交接协议

AI 代理在修改文档或交接任务时，应明确以下要素：

- **仓库位置**：记录本轮向用户确认的代码仓库根目录，或记录“未确认/本轮不访问”；未确认时不得假定路径，也不得据此推断代码现状。
- **目标与非目标**：清晰界定本次任务边界。
- **关联契约与约束**：关联对应 `REQ-*`、架构边界与安全策略。
- **修改范围**：明确允许变动的文件与兼容性要求。
- **交付证据**：记录实际执行命令、环境、工作树基线、通过/失败结果与剩余风险；不得编造测试通过事实。

## 6. 写作规范

- 文档用中文；代码、命令、标识符用英文。
- 长文档必须有一级标题、目录、章节编号。
- 代码块必须标注语言；围栏必须闭合。
- 表格列数保持一致。
- 内部链接使用相对路径；仓库文件使用相对于已确认仓库根目录的路径，并在任务记录中注明根目录，不写死本机绝对路径。
- 术语首次出现时给出英文/代码名。
- 不用“显然”“大家都知道”等模糊表述。
- 不写无法从源码/文档验证的结论；不确定时标“待确认”。
- 不写入密钥、令牌、密码、真实用户数据。
- 不粘贴大段三方文档；引用链接即可。
- 统计数据必须注明快照日期与统计口径。

## 7. 验证清单

修改后至少检查：

- [ ] 已向用户确认代码仓库位置，或明确记录“未确认/本轮不访问”
- [ ] 标题层级与目录锚点一致
- [ ] 代码围栏成对闭合
- [ ] 表格列数一致
- [ ] 本地链接目标存在
- [ ] 新/改的 `REQ-*` 有验收依据
- [ ] 三维状态有依据；已确认缺口已关联问题或风险编号，未核实项未被标成无缺口
- [ ] 没有把“计划”写成“已实现”
- [ ] 没有新增重复事实源，未把未核实项写成已完成
- [ ] 事实源映射与 `README.md` 第 5 节保持一致
- [ ] 数据快照日期已更新（如统计变化）
- [ ] 若仓库可见，对照修改前状态确认未擅自改动代码；已有未提交改动须保留，不要求工作树为空

可用只读命令：

```bash
# 查看文档规模（在本目录执行）
wc -l -c *.md

# 检查代码仓库是否被改动
# 先向用户确认仓库根目录，再替换下面的 <仓库根目录>
cd "<仓库根目录>" && git status --short

# 检查 Markdown 围栏数量（在本目录执行，应为偶数）
python3 - <<'PY'
from pathlib import Path

for path in sorted(Path(".").glob("*.md")):
    lines = path.read_text(encoding="utf-8").splitlines()
    fences = sum(1 for line in lines if line.strip().startswith("```"))
    print(f"{path.name}: fences={fences}")
PY
```

不要为了检查而安装新工具；需要新依赖时先询问。

## 8. 禁止行为

- 未经确认修改仓库代码、测试、示例或配置。
- 删除/覆盖用户已有的文档内容而不说明。
- 重写 git 历史、force-push、回滚他人工作。
- 提交密钥、凭据、`.env`、真实用户数据。
- 把 `demo.sqlite`、上传文件、日志加入文档或仓库。
- 声称“已通过安全审计/渗透测试”。
- 将未核实、未完成或存在影响验收缺口的契约说成已验证。
- 为了让数字好看而删除测试/契约。
- 在多个文档中维护互相矛盾的启动命令、配置默认值或测试计数。

## 9. 输出格式

完成文档修改后，回复至少包含：

1. **仓库位置确认**：本轮向用户确认的仓库根目录，或“未确认/本轮不访问”。
2. **改了哪些文件**
3. **核心变更**（按文档分组）
4. **验证结果**（TOC/围栏/链接/仓库状态）
5. **未解决项/风险**
6. **建议的下一步**（如有）

如果只改了文档，明确说明：

> 未修改任何项目代码；如仓库不可见，说明未核验仓库状态，不推断工作树是否为空。
