### 文档依赖与约束关系

下图的箭头表示“使用或受其约束”，**不是**文件必须依次编写或每次全部更新；单一事实源见第 3 节。

```text
README（索引、事实源） ──定位──▶ 各篇文档
AGENTS（本目录范围与执行协议） ──约束──▶ 本目录文档维护

requirements（预期行为） ──输入──▶ testing（测试设计） ──关联──▶ 仓库测试
architecture + spec（第 10、11、12 章）+ security ──约束──▶ 设计、实现和验证
spec（设计背景及历史实现说明） ──辅助理解──▶ 设计与代码核验
仓库源码/测试 ──证据──▶ 当前实际行为；examples/demo ──证据──▶ 示例行为
demo（示例说明） ──指向──▶ 仓库示例
gaps（开放缺口） ──引用──▶ 需求、测试、安全与发布状态
release（发布门禁与回滚标准） ──引用──▶ 需求、测试、安全和代码审查结果
```

需求、架构和安全是相互校验的约束，不是无条件的线性依赖：需求确定行为，架构限定可行边界，安全提供不可忽略的保护要求；发现冲突须由维护者判断，不能用单份文档自动覆盖其他事实。源码与测试反映实际状态，不自动等于预期；文档中对实现的描述须按 commit/快照核实。执行顺序见第 4 节。

## 4. 推荐工作流

按任务适用性执行，不要求全量阅读、线性走完全部步骤或同步所有文档。风险分级见 `AGENTS.md` 第 4.1 节；代码修改须获授权并遵守仓库规则。

1. 定义目标、非目标与受影响范围，按第 2 节选择最少必要材料。
2. 确认预期来源（适用的 `REQ-*` 或其他明确依据），按需评估架构、安全与兼容影响。
3. 只修改受影响的文件；测试、示例和发布检查按任务适用性执行。
4. 运行与风险匹配的验证，记录结果、未执行项和证据范围。仅需访问仓库时才确认其位置。

文档与代码/测试冲突时，按 [`AGENTS.md` 第 3 节](./AGENTS.md#3-事实源与冲突处理)处理。

## 5. 完成定义（Definition of Done）

本节定义**单次改动合并前**的最低要求。三段检查分工：合并前看本节；发版前的完整门禁见 [`release.md` 第 4 节](./release.md#4-发布前检查清单)；纯文档改动的格式校验见 [`AGENTS.md` 第 7 节](./AGENTS.md#7-验证清单)。

任何用户可见改动，合并前至少确认：

- [ ] 契约已更新，或明确说明“契约不变”
- [ ] 测试已新增/更新，并能在失败时定位问题
- [ ] 代码实现通过测试
- [ ] 安全影响已评估，`security.md` 的风险/检查清单已更新（如适用）
- [ ] 用户可见行为变化已评估是否更新 `demo.md` / `examples/demo`，适用时完成并验证
- [ ] 适用的文档构建 / 链接检查已执行并记录结果
- [ ] 实际可用的 CI 与相关测试已执行并记录结果；缺失的门禁标为待落地，不视为通过
- [ ] 没有提交 `demo.sqlite`、上传文件、日志、密钥

## 7. 治理规则与设计决策

本目录采用轻量级闭环治理，分工如下：

- **事实源映射**：在本文第 3 节统一维护唯一权威来源。
- **设计决策（ADR）**：在 [`architecture.md` 第 7.1 节](./architecture.md#71-设计决策记录规范adr) 规范 ADR 记录模板与决策矩阵。
- **AI 执行与漂移检测**：在 [`AGENTS.md`](./AGENTS.md) 维护变更风险分级、执行协议与验证清单。
- **术语规范**：在 [`glossary.md`](./glossary.md) 统一中英文名与使用规则。
- **发布与质量门禁**：在 [`release.md`](./release.md) 统一发布检查、代码审查清单与回滚动作。

它的目标不是重复领域实现细节，而是维护文档体系的稳定性与可追溯性。
