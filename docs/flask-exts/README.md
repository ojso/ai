### 文档依赖与约束关系

下图的箭头表示“使用或受其约束”，**不是**文件必须依次编写或每次全部更新；单一事实源见第 5 节。

```text
README（索引、事实源） ──定位──▶ 各相关文档
AGENTS（本目录范围与执行协议） ──约束──▶ 本目录文档维护

requirements（预期行为） ──输入──▶ testing（测试设计） ──关联──▶ 仓库测试
architecture + spec（第 10、11、12 章）+ security ──约束──▶ 设计、实现和验证
spec（设计背景及历史实现说明） ──辅助理解──▶ 设计与代码核验
仓库源码/测试 ──证据──▶ 当前实际行为；examples/demo ──证据──▶ 示例行为
demo（示例说明） ──指向──▶ 仓库示例
release（发布门禁与回滚标准） ──引用──▶ 需求、测试、安全和代码审查结果
```

需求、架构和安全是相互校验的约束，不是无条件的线性依赖：需求确定行为，架构限定可行边界，安全提供不可忽略的保护要求；发现冲突须由维护者判断，不能用单份文档自动覆盖其他事实。源码与测试反映实际状态，不自动等于预期；文档中对实现的描述须按 commit/快照核实。执行顺序见第 6 节。

## 6. 推荐工作流

以下是行为变更的默认顺序，不是要求所有文档每轮都修改。具体工作量按 `AGENTS.md` 第 4.1 节的风险分级调整；代码修改以用户授权和代码仓库规则为准。本目录 `AGENTS.md` 只约束文档，不授予代码仓库的修改权限。

不是单向瀑布，而是闭环：

```text
1. 契约/需求 + 架构/安全影响
   requirements.md（REQ-*）+ architecture.md + security.md
        │
        ▼
2. 测试设计（先红）
   testing.md 用例 + tests/ 失败测试
        │
        ▼
3. 实现（转绿）
   src/flask_exts/
        │
        ▼
4. 按需 Demo 验收
   examples/demo + demo.md
        │
        ▼
5. 文档与发布准备
   requirements.md / architecture.md / spec.md / testing.md / demo.md / security.md
        │
        ▼
6. CI 与验收
   unit + integration + coverage + docs + demo smoke
   + 发布/安全变更按 release.md 第 5 节做代码审查
        │
        └──────────────▶ 下一轮
```

| 步骤 | 必须产出 | 检查点 |
| --- | --- | --- |
| 1. 契约 | `REQ-*`、行为、边界、错误路径、架构/安全影响 | 是否与现有契约冲突？是否新增/修改 `REQ-*`？模块边界是否变化（同步 `architecture.md`）？是否改变认证/授权/令牌/CSRF/TFA？ |
| 2. 测试 | 用例 ID、失败测试 | 测试是否先于实现失败？是否覆盖错误路径与安全用例？ |
| 3. 实现 | 代码 + 通过测试 | 是否保持 Python 3.10+、公共 API 兼容？View/Admin 变更是否同步 `spec.md` 第 10 章？是否引入新秘密/日志泄露？ |
| 4. Demo | 适用时更新并验证示例/配置 | 如涉及示例，`demo.md` 第 11 章是否通过？是否使用 demo 默认凭据？ |
| 5. 文档 | 相关文档 | 是否出现新的事实源或过期数字？安全风险是否登记？ |
| 6. CI | 绿灯 + 报告 | 覆盖率、文档构建、demo 冒烟是否通过？发布/安全变更是否按 `release.md` 完成门禁与审查？ |

执行前先确定变更目标、范围、仓库 commit/工作树状态及相关文档修订。只有在适用时更新 demo、领域文档或执行对应检查；仓库不可见或门禁尚未建立时，记录未验证和原因，而不是宣称通过。先红不可执行时按 `testing.md` 第 2.3 节记录例外及证据。

常见路径：

- **新增/变更功能**：明确需求和架构、安全约束 → 确定或更新契约 → 设计并优先运行失败测试 → 实现 → 回归、适用的 demo 和审查 → 同步受影响文档。
- **修复缺陷**：核对原契约、复现问题 → 先写失败测试 → 修复 → 回归 → 更新实际受影响的状态和风险；契约不变不强行重写需求。
- **纯文档或无行为变化重构**：核对事实源与范围 → 修改 → 针对性验证；不强制编造新契约或 demo。
- **发布/安全变更**：在上述流程基础上增加安全、兼容性、审查与回滚检查，以 `release.md` 为准。

### 冲突处理规则

当“文档说 A、代码做 B”时：

1. **先判断哪边错**：是契约写错，还是实现偏离契约。
2. 契约错：更新 `requirements.md`，同步 `architecture.md`（边界/依赖）、`spec.md`（含 View/Admin）、`testing.md` 用例、`demo.md` 与 `security.md`。
3. 实现错：保留契约，先写失败测试，再修代码。
4. **禁止**直接把代码现状抄进文档来“消除冲突”。
5. 无法立即修复时，在 `spec.md` 第 7 章登记风险，在第 10.16 节登记 View/Admin 已知问题，在 `testing.md` 标“待补/待修”，安全相关风险登记到 `security.md` 第 11 节。

## 7. Definition of Done

- [ ] 契约已更新，或明确说明“契约不变”

## 12. 维护规则

### 12.1 更新顺序

1. 契约变化：先改 `requirements.md`，再同步 `spec.md` 与领域文档。
2. 测试变化：再改 `testing.md` 与测试代码。
3. 示例变化：再改 `demo.md` 与 `examples/demo`。
4. 发布变化：最后核对版本与文档一致性。
5. 本索引只在文档职责、状态、单一事实源或缺口变化时更新；具体编辑规则见 `AGENTS.md`。

### 12.2 状态标签

| 标签 | 含义 |
| --- | --- |
| 可用 | 与当前仓库校准，可作为工作依据 |
| 工作稿 | 结构完整，但部分基础设施/数据未落地 |
| 目标 | 尚未实现，不能当作现状 |
| 待补 | 尚无用例/实现 |
| 待修 | 已有测试/实现但不足或未触发缺陷 |
| 待更新 | 已知与源码/测试不一致，需要校准 |

### 12.3 版本与日期

- 每份文档顶部保留“文档版本 / 状态 / 最后更新”；涉及源码/测试事实的文档另加“数据快照”，治理类文档可标“不适用”。
- 版本号跟仓库版本或文档自身版本，不要混用。
- 统计数据变化时，必须同步更新快照日期。
- 发布时检查各文档的版本是否一致。

### 12.4 链接与事实检查

- 交叉链接使用相对路径（本目录内）或绝对仓库路径。
- 不复制大段配置表、命令、用例；使用“见某文档某节”。
- 新增事实前先查第 5 节：是否已有权威来源。
- 无法确认的事实标“待确认”，不要写成确定结论。
