## 0. 极速上手（5-Minute Quickstart）

新成员接入代码仓库（`flask-exts`）后，按以下三步拉起环境、启动示例与验证测试：

### 0.1 准备环境（Python 3.11+）

项目使用 [uv](https://docs.astral.sh/uv/) 管理虚拟环境与依赖；未安装时先按官方说明安装 `uv`。

```bash
# 在代码仓库根目录下执行
uv sync
```

> `uv sync` 会自动创建项目内 `.venv` 并安装运行时依赖及 `dev` 依赖组；该组包含测试工具与文档构建依赖（`docs` 组）。需要激活时执行 `source .venv/bin/activate`（Windows: `.venv\Scripts\activate`）；未激活时给命令加 `uv run` 前缀即可，例如 `uv run flask --app __init__ run`。

### 0.2 运行演示应用（Demo）

```bash
cd examples/demo

uv run flask --app __init__ run
# 浏览器访问后台: http://127.0.0.1:5000/admin/
```

> 首次启动时若 `examples/demo/demo.sqlite` 不存在，应用会自动建库并写入示例数据（含本地账号 `admin/admin`）；已有数据库不会被重建。首次启动后修改模型或示例数据，需删除该文件再启动或手动重建。
>
> 详细目录结构、数据模型与已知问题见 [`demo.md`](./demo.md)。

### 0.3 运行全量测试套件与覆盖率自检

```bash
# 回到代码仓库根目录
uv run pytest -q

# 测量测试覆盖率
uv run coverage run -m pytest -q && uv run coverage report
```

> 最近一次完整运行的通过/跳过数量、覆盖率数值、环境与快照日期统一见 [`testing.md` 第 1.1 节](./testing.md#11-当前规模)，本文不复制易过期的数字。

> 测试分层规范、用例清单与回归门禁详见 [`testing.md`](./testing.md)。

### 文档依赖与约束关系

下图的箭头表示“使用或受其约束”，**不是**文件必须依次编写或每次全部更新；单一事实源见第 5 节。

```text
README（索引、事实源） ──定位──▶ 各相关文档
AGENTS（本目录范围与执行协议） ──约束──▶ 本目录文档维护

requirements（预期行为） ──输入──▶ testing（测试设计） ──关联──▶ 仓库测试
architecture + spec（第 10、11、12 章）+ security ──约束──▶ 设计、实现和验证
spec（设计背景及历史实现说明） ──辅助理解──▶ 设计与代码核验
仓库源码/测试 ──证据──▶ 当前实际行为；examples/demo ──证据──▶ 示例行为
demo（示例说明） ──指向──▶ 仓库示例
release（发布门禁与回滚标准） ──引用──▶ 需求、测试、安全和代码审查结果
```

需求、架构和安全是相互校验的约束，不是无条件的线性依赖：需求确定行为，架构限定可行边界，安全提供不可忽略的保护要求；发现冲突须由维护者判断，不能用单份文档自动覆盖其他事实。源码与测试反映实际状态，不自动等于预期；文档中对实现的描述须按 commit/快照核实。执行顺序见第 6 节。

**来源边界：** 项目事实源为本目录 Markdown 文档与经用户确认访问的代码仓库（含其 Sphinx 文档和运行产物）。已登记的外部规范仅作对应领域的评估参考，不覆盖项目事实或契约；新增外部来源须先登记名称、URL、用途与适用范围。未登记的外部材料不作为事实依据。

### 兼容性与发布门禁

发布前门禁、代码审查清单、严重度门禁、回滚条件与发布说明模板统一在 [`release.md`](./release.md) 维护；本节不复制清单。涉及发布或兼容性判断时，按 `release.md` 第 3、4、5、7 节执行。

## 6. 推荐工作流

按任务适用性执行，不要求全量阅读、线性走完全部步骤或同步所有文档。风险分级见 `AGENTS.md` 第 4.1 节；代码修改须获授权并遵守仓库规则。

1. 定义目标、非目标与受影响范围，按第 3 节选择最少必要材料。
2. 确认预期来源（适用的 `REQ-*` 或其他明确依据），按需评估架构、安全与兼容影响。
3. 只修改受影响的文件；测试、示例和发布检查按任务适用性执行。
4. 运行与风险匹配的验证，记录结果、未执行项和证据范围。仅需访问仓库时才确认其位置。

文档与代码/测试冲突时，按 [`AGENTS.md` 第 3 节](./AGENTS.md#3-事实源与冲突处理)处理。

## 7. Definition of Done

任何用户可见改动，合并前至少确认：

- [ ] 契约已更新，或明确说明“契约不变”
- [ ] 测试已新增/更新，并能在失败时定位问题
- [ ] 代码实现通过测试
- [ ] 安全影响已评估，`security.md` 的风险/检查清单已更新（如适用）
- [ ] 用户可见行为变化已评估是否更新 `demo.md` / `examples/demo`，适用时完成并验证
- [ ] 适用的文档构建 / 链接检查已执行并记录结果
- [ ] 实际可用的 CI 与相关测试已执行并记录结果；缺失的门禁标为待落地，不视为通过
- [ ] 没有提交 `demo.sqlite`、上传文件、日志、密钥

**纯文档改动**按 [`AGENTS.md` 第 7 节](./AGENTS.md#7-验证清单)验证；本文不重复维护文档校验清单。

## 12. 维护规则

### 12.1 更新顺序

1. 契约变化：先改 `requirements.md`，再同步 `spec.md` 与领域文档。
2. 测试变化：再改 `testing.md` 与测试代码。
3. 示例变化：再改 `demo.md` 与 `examples/demo`。
4. 发布变化：最后核对版本与文档一致性。
5. 本索引只在文档职责、状态、单一事实源或缺口变化时更新；具体编辑规则见 `AGENTS.md`。

### 12.2 状态标签

文档元数据中的“状态”描述文档成熟度，不证明代码或测试现状已核实。项目事实以标明日期和范围的快照、源码检查或测试执行证据为准；契约验证状态见 `requirements.md` 第 2 节。

| 标签 | 含义 |
| --- | --- |
| 可用 | 文档可作为本目录的工作参考；不代表当前实现已核实 |
| 工作稿 | 结构完整，但部分内容或配套验证尚未完成 |
| 目标 | 计划行为或结构，不能当作现状 |
| 待补 | 指定范围尚缺用例、实现或证据 |
| 待修 | 已有内容不足或存在待修问题 |
| 待更新 | 已知内容与现有证据不一致，需要校准 |

### 12.3 版本与日期

- 每份文档顶部保留“文档版本 / 状态 / 最后更新”；涉及源码/测试事实的文档另加“数据快照”，治理类文档可标“不适用”。
- 版本号跟仓库版本或文档自身版本，不要混用。
- 统计数据变化时，必须同步更新快照日期。
- 发布时检查各文档的版本是否一致。

### 12.4 链接与事实检查

- 交叉链接使用相对路径（本目录内）或绝对仓库路径。
- 不复制大段配置表、命令、用例；使用“见某文档某节”。
- 新增事实前先查第 5 节：是否已有权威来源。
- 无法确认的事实标“待确认”，不要写成确定结论。
